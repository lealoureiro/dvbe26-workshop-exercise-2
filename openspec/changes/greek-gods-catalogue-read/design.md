## Context

The repository holds specifications but no implementation: no `pom.xml`, no `mvnw` wrapper, no `src/` tree, no CI, and `oas/greekController-oas.yaml` is a 0-byte file. `AGENTS.md` nevertheless documents `./mvnw clean verify` as the verification command and fixes the stack as Java 25, Spring Boot 4.0.x, Maven, PostgreSQL, and Flyway. This change therefore carries the project's scaffolding as well as its first capability.

See `proposal.md` — Why, for motivation, and `specs/greek-gods-catalogue/spec.md` for the requirements this design satisfies.

The governing constraint, established in the Functional Specification: the third party is the authority for **content** (which names exist), and this service is the authority for **identity** (which number denotes which god). A cache would relieve latency and leave identity unsolved; the split of ownership is what the design must express.

## Goals / Non-Goals

**Goals:**

- A schema whose shape makes the identity guarantee structural rather than a matter of discipline.
- A read path with no outbound network call.
- A published contract authored from the same source as the implementation.
- A test setup able to demonstrate identifier permanence, which requires a real database rather than an in-memory substitute.

**Non-Goals:**

- Populating the catalogue from upstream — that is `greek-gods-upstream-sync`, along with every question about cadence, triggering, and reconciliation.
- Pagination, filtering, sorting parameters, or any endpoint beyond the single read.
- Authentication, authorization, and rate limiting: the endpoint is specified as public.
- A deployment pipeline. No hosted environment exists.

## Decisions

**D1 — `greek_god(id, name)` with a case-insensitive unique constraint on `name` and a database-generated identity column.**
The unique constraint is what makes `name` a natural key in fact rather than by convention, and it is what lets the synchronization change be written as a plain conditional insert later. It is created case-insensitive here rather than altered later: `greek-gods-upstream-sync` needs that shape, neither change is implemented yet, and altering a constraint on a table created moments earlier is churn with no compatibility benefit — the table is necessarily empty until reconciliation exists, because this change ships no writer. Identity is generated by the database because the row is the only place identity exists; the alternative, deriving an id from the name by hashing, was rejected because it makes the id a function of content, so a corrected spelling upstream would silently change a published identifier — precisely the failure this design exists to prevent.

**D2 — No `DELETE` or `UPDATE` path against `greek_god` in this change.**
Decision D-1 in the Functional Specification makes synchronization insert-only. Establishing the table with no mutation path in the read change means the sync change starts from a structure that cannot recycle an identifier, rather than relying on the sync's own care.

**D3 — Read-only access in the request path, against the local schema only.**
Requirement "Serve the catalogue independently of the third-party service" is a claim about what the request does *not* do, so it is worth making structurally visible: nothing in the read path holds a client for the third-party service.

**D4 — Author the OpenAPI contract by hand, in `oas/greekController-oas.yaml`, and verify the served response against it in a test.**
`AGENTS.md` designates that file as the contract and requires it to match the code. Hand-authoring keeps the contract reviewable in isolation; a generated document would make the code its own specification, which cannot then disagree with it and so cannot catch drift. The match is asserted by test rather than by inspection.
Generating the Java type from the contract was considered: it would remove the duplicated record shape outright, which the third simple-design rule favours. It was rejected because the duplication is already guarded by a failing build, and because a hand-written contract plus a visible response type keeps the path from specification to code legible in a repository whose purpose is teaching. The duplication is accepted knowingly, not overlooked.

**D5 — Testcontainers for integration and acceptance tests; no in-memory database substitute.**
The guarantees at stake are sequence behaviour and a unique constraint, both of which an in-memory substitute emulates imperfectly. A guarantee tested against a different engine than it runs on is not tested. Requires a Docker runtime on the developer's machine.

**D6 — Return records in ascending identifier order, and state that order in the contract.**
Unknown U-4 left ordering unresolved. Unordered results are unstable across queries, and consumers depend on observed order whether or not it is promised, so staying silent defers the decision to whatever the query planner happens to do. Ascending identifier order was chosen over alphabetical because the catalogue is insert-only: new records append, and a record a consumer has already seen never shifts position. Alphabetical order was rejected for the opposite reason — every insert can move every later record — and because it would need an explicit collation decision to be repeatable at all.

**D7 — A plain layered shape: controller, repository, and a domain record.**
Three types carry this capability: an HTTP controller, a read-only repository, and a `GreekGod` record. Ports-and-adapters was considered and rejected for now: it would make "no third-party client in the request path" structural rather than reviewable, but it adds six-odd types to a two-field read, and Beck's fourth rule applies once correctness, clarity, and duplication are satisfied — which they are here. The structural claim in D3 is small enough to hold by review. Should `greek-gods-synchronization` grow a second inbound path, revisit this; introducing the outbound port at that point is a contained refactoring, not a rewrite.

**D8 — The identifier is a plain whole number on the published record, not a wrapper type.**
A `GodId` value type would prevent mixing this identifier with another, but there is only one identifier in this domain and nothing to confuse it with. The wrapper would add a type and a mapping step to guard against a collision that cannot occur. Revisit if a second identifier ever enters the model.

## Risks / Trade-offs

- **The endpoint delivers an empty array until the sync change lands** → Accepted and specified, not a defect: decision D-2 makes the empty catalogue a valid served state. It lets consumers integrate against a real contract before any data exists.
- **Scaffolding and first capability arrive in one change, enlarging the review** → Accepted. Scaffolding alone produces no observable behaviour and no spec, so a separate change would be decomposition by layer, which the planning constraints rule out.
- **Testcontainers requires Docker locally, and there is no CI to catch a machine without it** → Mitigated by naming the prerequisite in the tasks; unresolved beyond that, since no CI exists to enforce it.
- **A hand-authored contract can drift from the implementation** → Mitigated by D4's conformance test, which fails on drift rather than reporting it.
- **Preparation cannot be validated the way the two-step method intends** → Task 1.6 gates scaffolding behind a green build before any behaviour is added, which is the correct sequence, but "behaviour is preserved" is vacuous on a project with no behaviour yet. The gate proves the build works, not that nothing regressed. Recorded rather than papered over.
- **Permanence is asserted structurally in this change, not demonstrated dynamically** → Nothing here writes to the catalogue after creation, so no change-1 implementation could violate permanence and no change-1 test could detect one that did. The guarantee is held by the absence of a mutation path (D2) and is genuinely exercised in `greek-gods-upstream-sync`, where reconciliation can change records.

## Migration Plan

No migration. Nothing is deployed and there are no consumers. The Flyway migration that creates `greek_god` is the first, and applies to an empty database. Rollback is deleting the change; no data is at risk.

## Open Questions

None that can be deferred safely for this change. The three high-impact unknowns from the Functional Specification — sync cadence (U-1), what triggers a run (U-2), and upstream renames (U-3) — belong entirely to `greek-gods-upstream-sync` and do not affect these specs, this approach, or these tasks.
